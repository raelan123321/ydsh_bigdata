## Issue #3-01　订单状态的 4 个数字码语义无法还原

- **状态**：`OPEN`　**优先级**：P1　**类型**：数据质量 / 阻塞口径
- **现象**：`ods_order.order_status` 存在 `1 / 2 / 3 / 4` 四个纯数字取值，共 751 单（占 5.0%）。
- **已排查**：按状态分组统计金额分布，四种数字码的中位数（2,287~2,823 元）与其他状态（2,412~2,522 元）几无差异；
  与 `pay_amount` 正负、订单量、渠道均无相关性。**从数据本身无法推断映射关系。**
- **影响**：这 751 单无法判定是"已完成/已支付"还是"已取消/待支付"，只能归入"其他"并排除出 KPI，
  使 GMV 口径偏保守（可能少计最多 5%）。
- **处理方案**：本周先归入"其他"并在脚本注释、KPI 表 `calc_desc`、文档中三处显式标注；
  **不做猜测性映射**——猜错会把取消单计入 GMV，比少计更严重。
- **关闭条件**：拿到源系统状态码表，补 `dim_order_status_map` 维度表并回刷。
- **关联**：`sql/dwd/08_dwd_supplement.sql`、`CodeReview` CR-03、`AI洞察与反思` 第五节

## Issue #3-02　订单实付金额与订单明细金额不勾稽（差 11.26 倍）

- **状态**：`OPEN`　**优先级**：P1　**类型**：数据质量 / 口径一致性
- **现象**：`sum(dwd_order_item.item_amount)` = 2.62 亿，`sum(dwd_order_norm.pay_amount)` = 2.33 亿，
  比值 11.26×；单日口径同样稳定偏离 10~12 倍。
- **原因判断**：合成数据的订单表与明细表各自独立生成，`pay_amount` 并非由明细汇总而来，上游缺少勾稽约束。
- **影响**：品类/商品类金额指标**不能与 GMV 相加或换算**，只能做结构占比与排序；
  若对外报"品类销售额 3,970 万"会被误读为占 GMV 的 17%（实际口径不同）。
- **处理方案**：
  1. 报告中显式标注口径差异，`ads_category_top10.sales_share` 的分子分母都用明细口径（自洽）；
  2. `ai_insight.py` 增加"口径一致性校验"，比值超出 0.9~1.1 自动告警；
  3. 建议上游加规则：`abs(订单实付 - 明细金额之和) / 订单实付 <= 1%`，不通过阻断加载。
- **关闭条件**：上游补齐勾稽规则并重刷历史数据。
- **关联**：`CodeReview` 第二节、`AI洞察与反思` 第二节②、`output/week3/实跑结果记录.md`

## Issue #3-03　年度复购率恒为 100%，指标无区分度

- **状态**：`CLOSED`（已加月度口径规避）　**优先级**：P2　**类型**：指标设计
- **现象**：`ads_kpi_summary` 中复购率 = 100.00%。初看像计算错误。
- **核查**：1000 名用户全年 9,236 笔有效订单，人均 9.2 单，因此人人满足"≥2 单"。
  **计算没错，是年度口径在这份数据上没有信息量。**
- **处理**：保留年度值但加注说明；新增 `ads_kpi_month.repurchase_rate` 月度口径（28.68%~34.31%），
  对外汇报建议用月度值。
- **遗留**：若后续换成真实数据（人均 1~2 单），年度复购率会恢复正常，届时可去掉注释。
- **关联**：`sql/ads/11_kpi.sql`、`AI洞察与反思` 第一节③

## Issue #3-04　NL2SQL 大模型链路未实测，仅有离线链路结果

- **状态**：`OPEN`　**优先级**：P2　**类型**：验证缺口
- **现象**：评测报告显示"可执行率 100%、一致率 100%"，但运行模式为 `offline`，
  实际走的是关键词规则兜底，未调用大模型。
- **风险**：若直接把 100% 当作 NL2SQL 能力对外汇报，属于误导读数。
- **处理**：报告与文档中明确区分两种模式；评测脚本 `evaluate.py` 已支持 LLM 模式，
  配置 `LLM_API_KEY` 后重跑即可得到 LLM 口径的准确率与失败用例。
- **关闭条件**：拿到 API Key 后跑一次 LLM 模式评测，并把失败用例（预计集中在多表 join 与时间口径）写入复盘。
- **关联**：`docs/预测建模分析报告`、`output/nl2sql_eval.md`、`AI洞察与反思` 6.4

## Issue #3-05　订单明细为全量覆盖，未做增量同步

- **状态**：`OPEN`　**优先级**：P3　**类型**：工程健壮性
- **现象**：`08_dwd_supplement.sql` 中 `insert overwrite table dwd.dwd_order_item` 全量重刷，
  依赖 `dwd.dwd_order` 全量存在。
- **影响**：单次跑批可接受（15,000 单），但若订单表改为按日增量加载，明细表会因 join 不到历史订单而丢数。
- **建议**：订单表改增量后，明细表按 `order_date` 分区并同步增量覆盖对应分区。
- **关联**：`CodeReview` 第二节

## Issue #3-06　RFM 的观察期末日期硬编码

- **状态**：`OPEN`　**优先级**：P3　**类型**：可维护性
- **现象**：`ads_user_value` 计算 R 值时用 `datediff('2024-12-31', max(order_date))`，观察期末写死。
- **影响**：数据范围变化（如接入 2025 年数据）后 R 值会失真。
- **建议**：改为子查询 `(select max(order_date) from dwd_order_norm)`，或由调度系统传入变量。
- **关联**：`sql/ads/10_ads_tables.sql`
