# 第 5 周 · 个人项目反思日志

> 成员：刘正扬　|　日期：2026-11-23

## 一、技术维度

**掌握最扎实的**
- 四层数仓的职责边界：ODS 保留脏数据供审计、DWD 只管清洗建模、DWS 单次扫描落小表、ADS 面向应用组装——这套分层纪律是三周指标逐位一致的根本原因。
- Docker 编排的「可复现」思维：healthcheck 启动序、幂等初始化、命名卷持久化、密钥环境变量化，都是被真实故障逼出来的能力。

**仍需加强的**
- Hive 执行引擎与元数据管理的底层机制（Tez vs MR、Derby vs MySQL metastore）——本次踩坑后只做到「知其所以然」，还谈不上熟练。
- ClickHouse 只完成预留部署，尚未做 OLAP 加速实测；查询优化（索引/物化视图）经验不足。

## 二、协作维度

- **Git 工程化**：第 3 周坚持 feature 分支 + PR/CodeReview 留痕，第 4~5 周因一人直推主干——审查后意识到「规范不是为了评分，而是为了多成员协作时的可追溯」。若项目继续，将恢复分支流程。
- **AI 协作分工**：让 AI 做诊断、重灌、起草等重体力活，人负责口径确认与方案拍板。最大的教训是**必须给 AI 喂「实跑数据」而非让它自由发挥**，否则文档会悄悄失真。
- **文档即协作**：联调核对清单这种「可复跑的验收文档」比口头确认高效得多，以后每个集成节点都应留一份。

## 三、表达维度

- 演示叙事比功能堆砌重要：以「一笔订单的旅程」为主线（CSV → 四层仓库 → 大屏/问答）比罗列技术点更有说服力。
- 文档写作学到的核心是**口径先行**：指标定义不统一，后面所有对账都是灾难。
- 答辩问答预演发现的薄弱点：被问「为什么星型模型」时，答案要落在「DWS 聚合只 join 一次维度」的性能与简洁性上，而不是背概念。

## 四、改进计划（短期 → 长期）

1. 把 Hive 元数据后端从 Derby 迁到 MySQL metastore，消除单点（本次已预留 compose 配置）。
2. 用 ClickHouse 加速大屏接口，替换 MySQL 直查，压测对比 p50。
3. NL2SQL 接入真实 LLM（当前 offline 规则版），补充模糊问题的澄清交互。
4. 系统整理为可开源状态：补充 LICENSE、英文文档全覆盖、GitHub Actions 一键 CI。
