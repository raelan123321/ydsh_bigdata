## 四、问题与解决

- 遇到的问题：①Tez 计数器上限 120 导致 KPI 大查询失败且参数不可调；②Hive 3.1 中文别名触发 ParseException；③MySQL 元数据卷残留导致建表异常；④明细与订单金额不勾稽 11.26 倍；⑤NL2SQL 评测集含中文别名用例
- AI 是否有效解决：全部有效。KPI 脚本重构后单次扫描通过；别名改英文并同步修正 Prompt 规则与 fallback；元数据卷 down -v 重建；勾稽差异定位为折扣分摊口径并写入数据质量反思；评测集用例全部通过
- 最终如何解决：AI 定位根因并给出重构方案，人工确认业务口径后执行，实跑验证通过

## 五、反思与总结

- AI 协同带来的价值：从汇总建模、KPI 计算、预测对比到 NL2SQL 与智能洞察，一周内完成了原本需要多角色协作的完整分析链路；每次报错都有根因分析而非只给表面修复
- AI 的局限与风险（准确性 / 合规性 / 依赖）：模型结论（R² 为负、基线最优）必须结合业务数据形态人工复核；NL2SQL 的 LLM 链路依赖外部 API Key 与网络，离线兜底是必需的安全垫；数据口径问题（勾稽差异）AI 只能发现，业务解释必须人来定
- 本次协作中我的能力提升：掌握 DWS/ADS 分层设计方法、RFM 分层、三模型对比评估框架、NL2SQL 的 Prompt 工程 + SQL 安全闸门设计，以及 feature 分支 + PR + Code Review 的团队协作流程
- 对 AI 协同的改进建议：涉及口径的指标先让 AI 列出口径假设清单再计算；大 SQL 先做小样验证再全量跑，减少 Tez 环境的试错成本
